# Инструкции для всех ИИ-агентов

## Цель
Полный нативный перенос Cisco's Fantasy Medieval RPG [Dragonfyre] в Rust-движок Horizon с запуском через Horizon Offline Launcher. Java/Forge как runtime и «похожая» облегчённая RPG-сборка не принимаются. Нельзя удалять исходные основные механики ради производительности.

## Источники истины — в порядке приоритета
1. Актуальное локальное рабочее дерево и воспроизводимые результаты проверки.
2. GitHub `reports/AI_STATE.json` (с отметкой источника), подтверждённые Issues/коммиты и утверждённый пользователем roadmap.
3. `CURRENT_STATUS.md`, `ROADMAP.md`, `CONTEXT.md`.
4. Ранее записанные сообщения/отчёты без независимой проверки — только `REPORTED`.

**Не начинайте дальнейший этап, пока не проверены исходники, фактическая последняя сборка и незакрытая задача Stage 10.** Не предполагайте, что этот репозиторий уже содержит весь код.

## Доступ без пересылки файлов в чат

**Приватный репозиторий:** https://github.com/Ybuuc/dragonfyre-horizon-rust

**Первым делом** авторизованно прочитать `reports/AI_STATE.json`, `CURRENT_STATUS.md`, `docs/AI_ACCESS.md` и Issues #1/#2 с GitHub. Не просить пользователя снова прислать уже опубликованные исходники, контекст или результаты. Если GitHub недоступен, указать конкретную проблему с авторизацией — не угадывать содержимое. Текущие локальные результаты, отсутствующие в GitHub, нужно безопасно опубликовать: `scripts/sync-ai-state.ps1 -Push` (публикует только whitelisted summary; полные .exe, логи и данные игроков исключены). Другим ИИ с доступом к диску: делать `git pull` перед работой, `git commit` + `git push` после проверок; не полагаться на память чата.

## Передача работы между агентами

- Для команды «продолжи с места остановки» открой свежий `main` по ссылке на репозиторий. Прочитай этот файл и `handoff` в [reports/AI_STATE.json](reports/AI_STATE.json). Открой указанные Issue, ветку, коммит и PR (если есть). Сверь изменения после указанного коммита перед тем, как продолжать.
- При работе через авторизованный GitHub используй репозиторий напрямую. Для компиляции допустим временный checkout в облачной среде. Задачу, требующую Windows/Horizon, отмечай отдельно с конкретным тестом и артефактом, который нужно получить.
- Публикуй рабочий чекпоинт после каждого самостоятельного результата, до следующего длительного шага и перед завершением сессии. Обнови в `main` поле `handoff`: время с часовым поясом, статус, активное задание, ссылку на доступный коммит/ветку или PR, что сделано, что проверено, блокеры и один следующий воспроизводимый шаг. Держи `next_task` и `CURRENT_STATUS.md` в согласии с ним.
- Для незавершённого кода используй опубликованную рабочую ветку, а в `main` оставь ссылку на неё в `handoff`. После публикации перечитай запись из GitHub и проверь доступность указанного коммита. При параллельных изменениях перечитай свежий `main`, сохрани чужие результаты и не используй force-push.
- Если лимит или сбой прервал сессию, возобновляй работу по последнему опубликованному чекпоинту. Сверяй результаты с хешем сборки, к которой они относятся. Непроверенные шаги и проверка с подготовленными ресурсами должны быть явно обозначены.

## Первый запуск нового агента
- Сверить `git status`, `git log`, открытые Issues, названия веток и файлы проекта.
- Открыть документы Stage 07–10, `outputs/native-stage-10/pack-probe.log` (если он доступен), результаты `survival-first.json` и `survival-second.json`.
- Проверить источник `cisco_mod_legacy_2.5.jar` по лицензии и SHA-256, не загружая сторонние бинарники без права распространения.
- Проверить, что Stage 10 действительно запускается через **обычный** Horizon Offline Launcher, не подменяя действующий профиль временным.
- Зафиксировать, какие изменения реально существуют в Rust и пакетах, и что генерируется скриптами.

## Жёсткие правила
- Не утверждать «готово» по успешной компиляции, JSON, командам или демонстрации в тестовом мире без полной проверки механики.
- Не выдавать подготовленный тестовый инвентарь за естественное получение ресурсов в обычном выживании.
- Не заменять оригинальные предметы фиктивными без явной отметки `PARTIAL`.
- Не изменять исходные правила предметов, квестов, прогрессии и дропа без сравнения с оригиналом.
- Не создавать новые постоянные профили Horizon на каждую версию. Один профиль: `Dragonfyre`.
- Никогда не удалять пользовательские миры, пользовательские конфигурации и единственные копии исходников.
- Не выкладывать пароли, токены, приватные пути с секретами, чужие лицензированные бинарники или личные сохранения в Git.
- Минимизировать локальные дубликаты. Крупные архивы и сборки хранить в Google Drive; сначала проверить целостность загрузки.
- Всегда проверять обычный запуск через лаунчер, регрессии, сохранение/перезапуск и FPS на сопоставимых сценах.
- Исправлять корневую причину, а не скрывать ошибку отключением игрового функционала.
- Не добавлять собственные водяные знаки, подписи, логотипы, AI-брендинг и рекламные отметки в код, комментарии, документацию, отчёты, UI, изображения, видео, скриншоты, файлы сборок, сообщения коммитов и PR. В частности, запрещены вставки вида `Generated by ChatGPT/Claude/Codex`, `Made with AI`, рекламные ссылки и скрытые авторские метки ИИ-агента. Исключение — только явное указание владельца проекта.
- При этом сохранять обязательные лицензии, уведомления об авторских правах и корректную атрибуцию стороннего кода/ресурсов; не подделывать историю Git и не приписывать себе чужую работу. Технические записи о применённых инструментах, если они нужны для воспроизводимости, не являются рекламным водяным знаком.
- Отдельно вести известный краш звука Windows `0xc0000008`.
- Изменения в профиль/данные игры и очистку папок предварять резервной копией и оценкой риска.

## Процесс задачи
1. Выбрать ближайший непроверенный пункт **исходного** roadmap.
2. Описать начальное состояние, входные оригинальные механики, нужные изменения и приёмочный сценарий.
3. Изменять исходники/пакеты, сохранять воспроизводимость сборки.
4. Запустить unit/integration и игровые тесты, включая обычный GUI запуск.
5. Проверить регрессии Stage 06–09 и сохранения мира.
6. Сохранить точные команды, код выхода, хеш сборки, журналы, скриншоты и ограничения.
7. Обновить `CURRENT_STATUS.md`, `reports/AI_STATE.json` (или запустить безопасную синхронизацию с `-Push`), документацию этапа, Issue, коммит/PR. Убедиться, что GitHub действительно получил изменения, иначе они недоступны новому ИИ.

## Статусы
- `VERIFIED`: лично воспроизведено на конкретной сборке с доказательствами.
- `REPORTED`: известно только из прошлого отчёта.
- `PARTIAL`: реализован лишь фрагмент.
- `BLOCKED`: конкретный блокер с доказательством.
- `NOT STARTED`: работа не начата.
- `UNKNOWN`: недостаточно данных.

## Формат отчёта
**Задача / источник требований / до / изменённые файлы / выполнено / команды и фактические результаты / GUI и gameplay / регрессия / открытые ограничения / следующий шаг.**

Никогда не придумывайте процент готовности.
